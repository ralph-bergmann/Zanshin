## Intent

**Problem:** Zanshin has no `jj git push`, and its `Repo::clone` / `Repo::init` diverge from `jj git clone` / `jj git init` at v0.46.0: they never create the destination nor colocate, clone accepts a non-empty destination, writes one `clone` op instead of the CLI's three, writes no repo presets (`trunk()`), builds no start-up environment, reports no progress, and init ignores an existing `.git/` (deferred-work I1–I9). Epic 11's push sheet (11.8) needs a dry-run plan per mode, remote and ref.

**Approach:** Port `cmd_git_push` (every `GitPushArgs` parameter, dry run, sign-on-push, per-remote push, result reporting) as a new `zanshin-jj` verb with a pure planning phase, and re-port `cmd_git_clone` / `cmd_git_init` step for step over the existing creation path (destination rules, colocation, op split, presets, start-up environment, clean-up), all wired end to end (`.fbs` → zanshin-jj → `extern "C"` → `zanshin_core`) with the 6.4a progress pattern.

## Boundaries & Constraints

**Always:**
- The CLI at v0.46.0 is the spec (`git -C ../jj show v0.46.0:cli/src/commands/git/{push,clone,init,mod}.rs`, `cli/src/git_util.rs`): preconditions and their order, refusal texts verbatim, op descriptions byte-identical, every on-disk effect (repo-level config presets, `.jj/.gitignore`, created/removed directories, git refs). Terminal UX (status lines, progress bars, `$EDITOR`) is replaced by typed data.
- Every CLI parameter is passed through (FR-JJ-17); config-driven defaults (`git.push`, `git.colocate`, `git.object-hash`, `revsets.git-push`, `git.private-commits`, `git.sign-on-push`, `git.track-default-bookmark-on-clone`, `remotes.<r>.fetch-bookmarks/fetch-tags`) are read from the effective config stack, never baked in. Absence is `None`/null. Tri-state colocation crosses the wire as the CLI's two flags (`colocate`, `no_colocate`; both set → `jj.invalid_input`), as `WorkspaceAddRequest` does.
- Push is ONE transaction on one base op; the planning phase (remote resolution, `-c`/`--named` naming and checks, mode targets, classification, commit validation, op description) is a pure function shared by the dry run and the real run — a dry run writes no operation besides the pre-verb snapshot's.
- Hints the UI shows verbatim (per-ref refusal hints, commit-rejection hints, the "only existing remote" hint, the push-stats hints) are typed result data; every CLI `Warning:` line on a ported path is a registered 9.32 warning code with the CLI text verbatim (the oracle compares warning COUNTS).
- Once the push loop has started, the outcome is returned as data (per remote: refs pushed / lease-rejected / remote-rejected / unexported; which remotes finished; recorded or not; the failure "Failed to push some bookmarks" or the hard `GitPushError` text) on an OK envelope; refusals before any network are errors.
- Clone writes the CLI's three operations through `mutate::finish_transaction` (each skipped when its transaction has no changes, the CLI's "Nothing changed."), so identity / became-immutable / colocated export warnings happen per finish.
- Clean-up scope = the CLI's: only failures inside init-workspace / add-remote / fetch remove `<dest>/.jj` (and `<dest>/.git` when colocated) and then the destination directory iff the call created it; failures after (presets, checkout, re-open) keep the workspace. Init never cleans up beyond jj-lib's own `.jj` removal.
- Never regenerate fixtures; no test reaches the network (local bare repos / `file://` sources only); every new extern gets a `packages/zanshin_core` real-cdylib test on a path that spawns no git (the Dart VM reaps children).

**Never:**
- No UI widget code (the projects window keeps its own clone-destination port and its form; only the `WorkerProjectRepos` adapter changes, to keep the commands it displays). No MCP tool. No cancellation and no live-delivery change (deferred).
- No jj template rendering: `--change` uses the builtin default name only; a customised `templates.git_push_bookmark` refuses (deferred).
- No `jj git init --git-repo` arm (Zanshin's `convert` verbs own the external flows); no `--at-op` / `--ignore-working-copy` / `--no-integrate-operation` (no Zanshin counterpart). `remotes.<r>.auto-track-bookmarks` in clone stays Story 9.30's.
- Never lower the coverage baseline or add an `exclude_prefix`.

## Design Notes

- **Push failure as data.** Once a push has started, jj may have changed remotes even when it fails (a lease failure after an export, a second remote unreachable after the first succeeded). The UI must show per-remote, per-ref results and whether Undo works (epics 9.20 item 8), which an error envelope cannot carry. So the verb returns `Ok(GitPushOutcome)` with `failure` set, and the oracle treats `failure.is_some()` as the CLI's non-zero exit. Refusals before the network stay `Err` with registered codes: `jj.invalid_input` (flag conflicts, `--named` syntax, "No git remotes to push to", template failures), the codes `MutateError::BookmarkExists` / `BookmarkTrackedRemoteExists` already map to (ensure_new_bookmark_name), `jj.revset_parse_error` / `jj.revset_resolution_error`, `jj.config_error`, precondition codes, and the two new codes `jj.push_ref_refused` / `jj.push_commit_rejected` for an explicit target's refusal or rejection (message = CLI text; the hint travels in the dry-run plan).
- **Dry run never aborts on a per-ref refusal.** The CLI's dry run errors on an explicit target's refusal like the real run. Zanshin's dry run instead returns the whole plan with that row marked abort and `failure` set to the CLI's error text, so 11.8 can block the row and still show the rest (epics item 2); the oracle still sees "refused". Name-level errors (`--named` syntax, existing bookmark, template) stay `Err` in both runs (epics item 6 "the dry-run reports these errors").
- **Paths.** `source`, clone `destination` and init `path` cross verbatim; a relative path resolves against the process cwd exactly as the CLI's `cwd.join` does (the GUI passes absolute paths). The source URL is not re-absolutised (`absolute_git_url` is terminal-cwd UX; existing stance `git.rs` ~:466-470).
- **Two classifications per candidate** (epics item 2): the mode's own `ClassifyParams` decides skip vs push; the explicit one (`allow_new = !has_tracked_remote_bookmarks`, `allow_delete = true`) tells 11.8 whether a skipped row could still be ticked by hand.
- **Clone progress correlation.** The clone extern allocates the session id first and tags progress with it; the worker maps it once the handle is registered. Because the worker handles events after the command returns (deferred), this is enough for correlation today and stays correct once delivery becomes live (the worker then needs a pending-creation map — part of that deferral).
- **Init modes.** `Backend::None` (native) is Zanshin-only and stays as is. `Backend::Git` follows `do_init`: Internal, Colocate, or the External flow over an existing `.git` (delegated to the convert-colocated steps, which already port IN:249-282 incl. the linked-worktree warning).
- **Deferred-item outcomes expected from this spec:** I1 fixed (destination rules), I2 fixed (presets + `trunk()` read-back), I3 rejected as worded (jj-lib's `init_with_factories` removes `.jj` itself; witnessed) with the residual = CLI parity, I4 partly done (alias tables + `immutable_heads()` + became-immutable; template / short-prefixes parses remain 9.32's deferral), I5 + I7 fixed (op split), I6 fixed (External flow / refusal), I8 fixed (`jj.destination_not_empty` before creation), I9 partly done (destination rules + progress over the bridge; cancel and live delivery deferred; app-side port removal is UI work the story text does not ask for).
