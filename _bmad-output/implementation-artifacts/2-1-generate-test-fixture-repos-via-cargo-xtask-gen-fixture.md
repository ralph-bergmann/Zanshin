## Story

As a developer running tests against jj repositories,
I want two pre-built jj repo fixtures (`tiny-3-commits`, `medium-1k-commits`) committed to the repo as `.tar.zst` archives generated by `cargo xtask gen-fixture`, plus a `test_helpers::extract_fixture(name)` helper that unpacks them at test time,
So that every subsequent story (2.3+, Epics 3–7) tests against version-controlled fixtures and the test suite never shells out to the `jj` CLI (per AR-P-7 / NFR-R-1).

This story establishes the **test-fixture infrastructure** for Epic 2 and the rest of the workspace. It is the first crate to consume `jj-lib`, so it also lands the `[workspace.dependencies]` entry that Story 2.3 (`repo.rs`) will reuse.

## Acceptance Criteria

Grouped by deliverable. Each item is a checkable contract; the "Given/When/Then" source is `epics.md#Story 2.1` unless noted.

### AC-1 — `gen-fixture` task exists and is jj-lib-backed

1. `crates/xtask/src/tasks/gen_fixture.rs` exists and implements a task invocable as `cargo xtask gen-fixture --size <tiny|medium>` **and** `cargo xtask gen-fixture --all`.
2. The task constructs the fixture repos **using `jj-lib` directly** — **NO** shelling to the `jj` CLI, **NO** string-parsing of `jj` output (AR-AP-1/AR-AP-2, NFR-R-1). Construction happens in a `tempfile::TempDir`, which is then tar'd and zstd-compressed to `test-fixtures/repos/<name>.tar.zst`.
3. `--size large` is **not implemented** in WIP. Either omit the variant entirely or accept it and exit with a clear "deferred to release phase" message — do **not** silently produce a partial archive. (Recommended: omit; document in the README.)
4. The `xtask` `main.rs` dispatches to the task (replacing the `fn main() {}` placeholder).

### AC-2 — `tiny-3-commits` fixture

5. `cargo xtask gen-fixture --size tiny` writes `test-fixtures/repos/tiny-3-commits.tar.zst` containing a jj repo with **exactly 3 commits in a linear chain** (plus jj's implicit root commit).
6. All commits use a **single author identity** `Fixture <fixture@zanshin.test>` and **fixed timestamps** (e.g. a constant Unix-epoch base, incremented per commit). *(Fixed values are for stable, reviewable fixtures — see "Determinism" note below; byte-identical cross-machine reproduction is **not** a required guarantee in WIP.)*
7. The archive is **< 50 KB** compressed.

### AC-3 — `medium-1k-commits` fixture

8. `cargo xtask gen-fixture --size medium` writes `test-fixtures/repos/medium-1k-commits.tar.zst` containing a jj repo with **exactly 1000 commits**.
9. The DAG has **~30 bookmarks** distributed across it.
10. The DAG contains **at least one branching point with 3 parallel branches that later merge** (exercises multi-parent / merge-commit handling for Epic 4's lane algorithm).
11. Same fixed author identity + fixed timestamps as AC-6.
12. The archive is **< 5 MB** compressed.

### AC-4 — committed artefacts, git config, README

13. Both `.tar.zst` files are committed under `test-fixtures/repos/`.
14. A root `.gitattributes` declares `test-fixtures/**/*.tar.zst binary` so git never attempts text diffs/merges on them.
15. There is **no** `.gitignore` rule that would exclude the fixtures (current `.gitignore` ignores only `target/`, `_bmad/`, `.claude/`, `.serena/`, IDE files — fixtures are safe; verify this still holds, and do not add a broad `*.tar.zst` ignore).
16. `test-fixtures/repos/README.md` documents: which fixtures exist, what each contains, how to regenerate (`cargo xtask gen-fixture --all`), the `zstd -19` choice, and that fixtures are committed/reviewed (not rebuilt at test time). It also notes that `large-10k-commits` is deferred to the release phase.

### AC-5 — `extract_fixture` test helper

17. A reusable helper `test_helpers::extract_fixture(name: &str)` exists and is consumable as a **dev-dependency** by integration tests in any workspace crate (`zanshin-jj` first, in Story 2.3). See "Decision D1" for where it lives.
18. `extract_fixture("tiny-3-commits")` extracts the matching `.tar.zst` into a **per-call temp directory**, returns a handle exposing the **path to the extracted workspace root** (the directory containing `.jj/`), suitable for `Workspace::load` / the future `Repo::open`.
19. Cleanup is **automatic via `Drop`** on a `tempfile::TempDir` owned by the returned handle. (The handle must keep the `TempDir` alive for as long as the caller holds the path.)
20. The helper resolves the archive path relative to the workspace root via its own `env!("CARGO_MANIFEST_DIR")`, so it works regardless of which crate's tests call it.

### AC-6 — `--all` and runtime budget

21. `cargo xtask gen-fixture --all` regenerates **both** fixtures (sequential or parallel — implementation choice).
22. `--all` completes in **< 60 seconds** on a developer machine (M1 Max baseline) for tiny + medium.

### AC-7 — quality gate stays green

23. `cargo make test` passes end-to-end. Specifically: `cargo clippy --workspace --all-targets -- -D warnings` (pedantic on) is clean, `cargo fmt --all --check` is clean, `cargo test --workspace` passes, and `cargo make`'s `test-cargo-hygiene` gate passes (see "Decision D1" for the crate-count interaction).
24. Every new `.rs` file starts with `// SPDX-License-Identifier: Apache-2.0` on line 1.

### Edge cases (must hold)

25. **Relocatable fixture:** the extracted repo opens successfully from a temp path **different** from where it was generated (jj repos are designed to be relocatable, but the git backend / working-copy state inside `.jj/` must not embed the original absolute path in a way that breaks `load`). Add a test that extracts and loads from a fresh tmpdir. *(If `load` is not yet available — it lands in Story 2.3 — assert instead that the extracted tree contains a well-formed `.jj/repo/` and `.jj/working_copy/`; upgrade to a real `Workspace::load` assertion in Story 2.3.)*
26. **Compression level:** the gen task compresses with **`zstd` level 19** (high compression — paid once at generation, never at test time).
27. **No `unwrap`/`expect`/`panic!` on reachable error paths** in the gen task or the helper beyond genuinely-unreachable invariants; propagate errors. (xtask is a CLI binary, so returning `Result` from a fallible `run()` and surfacing via `main` is the idiom — see Dev Notes.)

## Dev Notes

### Decision D1 — where `extract_fixture` lives (RECOMMENDED: new `crates/test-helpers` crate)

The AC names the helper `test_helpers::extract_fixture` — a `test_helpers::` path strongly implies a **crate** named `test-helpers` (crate root `test_helpers`), not a per-crate `tests/common/mod.rs` (which would be `common::extract_fixture` and would be **duplicated** across `zanshin-jj`, `zanshin-graph`, `zanshin-diff`, `zanshin-ffi` tests). A shared crate is the DRY, production-grade choice and matches how the helper is reused in Stories 2.3, 2.10, 4.x, 5.x.

**Recommended structure:**
- New crate `crates/test-helpers` — package name `test-helpers`, lib name `test_helpers`, a plain `lib` (NOT a cdylib).
- Deps: `tar`, `zstd`, `tempfile` (via `{ workspace = true }`).
- It is **test-only**: it is automatically excluded from `default-members` (which is an *explicit* list that already omits `xtask`), so `cargo build --release` skips it. `cargo test --workspace` and clippy still cover it.
- Consuming crates add `test-helpers = { path = "../test-helpers" }` under `[dev-dependencies]` (Story 2.3 onward; this story only needs it for its own smoke test).

**⚠️ CRITICAL interaction:** `Makefile.toml`'s `test-cargo-hygiene` task hard-asserts **exactly 7** tracked `Cargo.toml` files (root + 6 crates) and fails the whole `cargo make test` if the count differs. Adding `test-helpers` makes it **8**. You **must** bump `-ne 7` → `-ne 8` and update the surrounding comment/message in the same change (see T8). This guard exists precisely to force this revisit. [Source: Makefile.toml:118-125]

**Alternative (only if Ralph vetoes a new crate):** put `extract_fixture` in `zanshin-jj` as a `#[cfg(any(test, feature = "test-helpers"))]`-gated `pub mod test_helpers` — but this pollutes the anti-corruption layer's deliberately-minimal public surface and is **not recommended**. Flagged as an open question below.

### jj-lib 0.41.0 API — verified anchors (⚠️ churny — verify each against `cargo doc -p jj-lib` / docs.rs for 0.41.0 before relying on it)

jj-lib is pinned `=0.41.0` and is pre-1.0; signatures drift between minor versions. The following were confirmed from the docs.rs 0.41.0 pages, but **the dev MUST re-verify** — especially the tree-construction path and `Transaction::commit`'s exact return type.

**Workspace init (all `async`):** [docs.rs/jj-lib/0.41.0/jj_lib/workspace/struct.Workspace.html]
```rust
pub async fn init_internal_git(           // ← use this: jj repo backed by an internal (bare) git store
    user_settings: &UserSettings,
    workspace_root: &Path,
) -> Result<(Self, Arc<ReadonlyRepo>), WorkspaceInitError>
// also: init_simple (native backend), init_colocated_git, init_external_git
pub fn load(user_settings, workspace_path, store_factories, working_copy_factories)
    -> Result<Self, WorkspaceLoadError>   // (Story 2.3 uses this)
```

**UserSettings:** [docs.rs/.../settings/struct.UserSettings.html]
```rust
pub fn from_config(config: StackedConfig) -> Result<Self, ConfigGetError>
```
Build a minimal `StackedConfig` from `jj_lib::config` — start from jj-lib's default config layer and push a layer setting at least `user.name` / `user.email` (and anything `from_config` requires, e.g. operation/store settings). **This is the #1 churn-risk area** — read jj-lib 0.41.0's `config` module and, for the exact recipe, jj's own `lib/testutils/src/lib.rs` at tag `v0.41.0` (it builds a `UserSettings` for tests). Note: because we set author/committer explicitly on each `CommitBuilder`, the config identity is a fallback only.

**Transaction + commit creation:** [docs.rs/.../repo/struct.ReadonlyRepo.html, struct.MutableRepo.html, commit_builder/struct.CommitBuilder.html]
```rust
pub fn start_transaction(self: &Arc<Self>) -> Transaction          // SYNC
// on MutableRepo (via tx.repo_mut()):
pub fn new_commit(&mut self, parents: Vec<CommitId>, tree: MergedTree) -> CommitBuilder<'_>
pub fn set_local_bookmark_target(&mut self, name: &RefName, target: RefTarget)
// CommitBuilder (consuming builder):
.set_author(Signature) .set_committer(Signature) .set_description(impl Into<String>)
.set_parents(Vec<CommitId>) .set_tree(MergedTree)
pub async fn write(self) -> BackendResult<Commit>                   // ASYNC
// then: tx.commit(description)  →  verify exact signature/return (likely BackendResult<Arc<ReadonlyRepo>>)
```

**Signature / fixed timestamps:** construct `jj_lib::backend::Signature { name, email, timestamp: Timestamp { timestamp: MillisSinceEpoch(<fixed>), tz_offset: <fixed> } }` (verify field/type names for 0.41.0). Use the same identity everywhere; increment the millis per commit for a sensible ordering.

**Tree construction (the other churn-risk area):** each commit should touch ≥1 file (realistic trees, needed by later diff/graph stories). Path in 0.41.x is roughly: write file content to the backend store (`repo.store().write_file(...)` → `FileId`), assemble a tree with a tree/merged-tree builder, get a `MergedTree`. **Read jj's `testutils` (`create_tree` / `write_random_commit` / `CommitGraphBuilder`) at `v0.41.0` for the canonical recipe** — do not guess. An empty-tree commit is acceptable as a fallback only if non-empty trees prove too costly, but prefer non-empty.

**Bookmarks:** `RefName` and `RefTarget` live in `jj_lib::ref_name` / `jj_lib::op_store`. Use `RefTarget::normal(commit_id)` for a non-conflicted bookmark. Verify the `RefName` constructor (`RefName::new`/`from` and owned vs borrowed) for 0.41.0.

### Async — driving jj-lib's futures from a sync xtask

`init_internal_git`, `CommitBuilder::write`, and `rebase_descendants` are `async`, but `start_transaction`/`tx.commit` are sync. jj-lib's async is executor-agnostic for the local git/native backends (no tokio reactor needed). **Recommended:** add `pollster` and wrap each async call in `pollster::block_on(...)` — lightweight, zero project-wide implications, and `xtask` is excluded from release builds anyway. *Fallback:* if a backend op turns out to need a tokio reactor, use a current-thread `tokio::runtime::Runtime` instead. Do **not** make this imply that production crates adopt tokio (project-context: "tokio only where required by a dependency").

### Determinism (WIP posture)

The byte-identical-across-machines *guarantee* and the fixture-versioning ACs are **dropped** for WIP. **Still do** use a fixed author identity and fixed timestamps (AC-6/AC-11): it keeps fixtures stable and review diffs small, and avoids gratuitous churn — it's good engineering, just not a contractual guarantee. Do not invest in seeding every source of nondeterminism (jj change-ids are random by default; that's fine in WIP). If a future story needs strict determinism, it returns in the release phase.

### Testing standards (project-context § Testing Rules)

- Rust unit tests inline (`#[cfg(test)] mod tests`); integration tests in the crate's `tests/`.
- Tests must **not** depend on `~/.jjconfig.toml` / `~/.gitconfig`; pin `JJ_CONFIG` / `GIT_CONFIG_GLOBAL` to a fixture-controlled value where relevant (the gen task and helper should not read user globals — the explicit `UserSettings`/`Signature` already avoid this; just don't reintroduce a global read).
- No network. No `#[ignore]`/skip for flakiness. Tests run in parallel by default.
- This story produces **no JSON crossing the FFI boundary**, so the schema-validation rule does not apply here.
