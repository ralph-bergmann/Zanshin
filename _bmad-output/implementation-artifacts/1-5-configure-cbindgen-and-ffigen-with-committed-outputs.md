2. **AC-2 — `zanshin-ffi/src/lib.rs` declares a minimal `zanshin_ffi_version()` placeholder.** The current placeholder comment in `crates/zanshin-ffi/src/lib.rs` (Story 1.1 state: `//! Placeholder for the zanshin-ffi cdylib boundary crate. Body lands in Epic 3.`) is replaced with a minimal compilable `extern "C"` symbol that gives cbindgen something to extract:
   ```rust
   // SPDX-License-Identifier: Apache-2.0

   //! `zanshin-ffi` — single cdylib FFI boundary for the Zanshin Rust core.
   //!
   //! WIP scope (Story 1.5): only the `zanshin_ffi_version()` build-stamp symbol is
   //! declared here, so `cargo make codegen` has at least one `extern "C"` function
   //! to lift into `include/zanshin_ffi.h` and `app/lib/src/ffi/bindings.dart`. The
   //! full FFI surface (envelope, handle helpers, panic-catch wrapper, repo/diff/
   //! graph/watcher wrappers) lands in Epic 3. The full `zanshin_ffi_version()`
   //! implementation with `build.rs` git-SHA injection and CString allocation lands
   //! in Story 3.2.

   use core::ffi::c_char;

   /// Build-stamp version string. WIP-placeholder: returns a static C-string
   /// pointer to the crate version. Story 3.2 replaces this with a heap-allocated
   /// `<version> (<git-sha>)` string via `ffi_strings::string_to_cstring` and a
   /// `build.rs` that injects `ZANSHIN_GIT_SHA` at compile time.
   ///
   /// # Safety
   /// The returned pointer is a `'static` literal — the caller MUST NOT free it.
   /// Story 3.2's replacement returns a heap pointer and gets `zanshin_string_free`
   /// as its destructor pair; the placeholder does not.
   #[no_mangle]
   pub extern "C" fn zanshin_ffi_version() -> *const c_char {
       // WHY: static null-terminated literal — no allocation, no build.rs needed
       // for the Story 1.5 codegen-plumbing bootstrap. Replaced wholesale in 3.2.
       b"0.1.0\0".as_ptr().cast::<c_char>()
   }
   ```
   - **Why not the full Story 3.2 implementation?** Story 3.2 owns `build.rs` + `ffi_strings::string_to_cstring` + the `CString::from_raw` free-function discipline. Story 1.5's job is "make `cargo make codegen` produce committed output" — the minimum `extern "C"` shape that fits the AR-P-3 module layout. The placeholder is intentionally trivial and gets replaced wholesale; no premature scaffolding (per `project-context.md` § Critical Don't-Miss Rules — "Don't add features beyond what the task requires").
   - **Why `*const c_char` and not `*mut c_char`?** A `'static` literal is read-only and must never be freed. Story 3.2 will change the signature to `*mut c_char` (heap allocation, paired with `zanshin_string_free`). The change of return type is a breaking FFI change, but that's exactly what WIP-rework allows: the placeholder ships ONE caller (none, since Epic 3 hasn't wired the Dart-side worker yet), Story 3.2 swaps the signature and regenerates `zanshin_ffi.h` + `bindings.dart` in the same PR. No `_v2`, no in-wire version-shim (per `project-context.md` § "WIP: breaking changes are allowed").
   - **Why `core::ffi::c_char` and not `std::os::raw::c_char` or `libc::c_char`?** `core::ffi::c_char` is the modern stable-since-1.64 platform-independent definition; available in `no_std` contexts; no extra dep. The other forms are equivalent on macOS but pull `std`/`libc` for no benefit here.

3. **AC-3 — `app/ffigen.yaml` exists with documented config.** A new file at `/Users/ralph.bergmann/development/projects/privat/Zanshin/app/ffigen.yaml` declares at minimum:
   - `name: 'ZanshinFfi'` — the generated Dart class wrapping the symbol table
   - `description: 'FFI bindings for the Zanshin Rust core. Auto-generated by ffigen — DO NOT EDIT. Regenerate via `cargo make codegen`.'`
   - `output: 'lib/src/ffi/bindings.dart'` (relative to `app/`, the file ffigen writes — the canonical location per AR-P-6)
   - `headers.entry-points: ['../crates/zanshin-ffi/include/zanshin_ffi.h']` (the cbindgen output, one directory up from `app/`)
   - `headers.include-directives: ['../crates/zanshin-ffi/include/zanshin_ffi.h']` so ffigen does NOT recurse into `<stdint.h>` / `<stdbool.h>` and generate Dart bindings for system types. Without this, ffigen pulls system-header symbols (e.g., `__int128_t`, `__darwin_*` typedefs) into the output and the generated `bindings.dart` is hundreds of lines of macOS-SDK noise. The include-directives explicit allow-list is the canonical ffigen idiom for this constraint (see ffigen 20.1.1 docs — also confirmed empirically at story-write time).

   - `comments.style: 'doxygen'` and `comments.length: 'full'` so cbindgen-lifted doc comments from `extern "C"` declarations come through. (`zanshin_ffi_version`'s doc comment is one example; Epic 3 functions will have richer docs.)
   - **NO `preamble:` field** for an auto-generation banner. ffigen ALWAYS prepends `// AUTO GENERATED FILE, DO NOT EDIT. By ffigen` at the top of every output by default — duplicating it via `preamble` would produce two banners.
   - **NO SPDX header in `bindings.dart`.** The generated file is auto-managed; SPDX on a generated file would be either (a) prepended by ffigen and need re-injection on every regen — fragile, or (b) hand-edited — violates AR-AP-7. The repo-root `LICENSE` covers it. `project-context.md` § Documentation says "SPDX on every source file" — the implicit carve-out for generated code is documented here. (This carve-out aligns with `architecture.md` § P-9 — SPDX is for hand-written `.rs` / `.dart`.)

### What this story is NOT

This story is the **codegen plumbing bootstrap** — it lands the configs (`cbindgen.toml`, `ffigen.yaml`), the minimum Rust placeholder needed to drive cbindgen, the first committed codegen outputs, and the deferred-work absorption (the `git diff --quiet` precondition). It is **NOT**:

- A full `zanshin_ffi_version()` implementation. Story 3.2 owns: `build.rs` with `git rev-parse HEAD` → `ZANSHIN_GIT_SHA`, `ffi_strings::string_to_cstring` heap-allocation helper, `zanshin_string_free` pair, and the `<version> (<git-sha>)` formatted output. The placeholder here returns a `'static` `b"0.1.0\0"` literal — intentionally trivial, get-replaced-wholesale.
- A typed Dart wrapper around `bindings.dart`. The Dart Worker isolate (Story 3.9) and the typed result classes (`app/lib/src/domain/`) come later. Story 1.5's `bindings.dart` is RAW ffigen output — `Pointer<Char>` not `String`, no convenience wrappers, no isolate ports. Future Dart code consumes `bindings.dart` directly.
- The CI codegen-drift gate. Per `epics.md` § Story 1.5 WIP-rework note, the CI gate is deferred to the release phase. `cargo make verify-codegen` is a manual discipline tool here (Story 1.4 AC-5) and Story 1.5 only makes it work end-to-end.
- Lint / format config tightening. Story 1.7 owns `[workspace.lints]`, `rustfmt.toml` enhancements, `analysis_options.yaml` cleanup. Story 1.5 only patches `app/ffigen.yaml`'s `preamble:` if ffigen-generated code trips analyzer lints (per AC-16 — the targeted, file-scoped `// ignore_for_file:` pragma).
- The Epic 3 FFI module surface (`envelope.rs`, `handle.rs`, `ffi_strings.rs`, `repo.rs`, `diff.rs`, `graph.rs`, `watcher.rs`). The placeholder `zanshin_ffi_version` is intentionally in `lib.rs` and NOT in a separate module — the AR-P-3 module breakdown is Epic 3's concern.

### Placeholder `zanshin_ffi_version()` — complete `crates/zanshin-ffi/src/lib.rs`

```rust
// SPDX-License-Identifier: Apache-2.0

//! `zanshin-ffi` — single cdylib FFI boundary for the Zanshin Rust core.
//!
//! WIP scope (Story 1.5): only the `zanshin_ffi_version()` build-stamp symbol is
//! declared here, so `cargo make codegen` has at least one `extern "C"` function
//! to lift into `include/zanshin_ffi.h` and `app/lib/src/ffi/bindings.dart`. The
//! full FFI surface (envelope, handle helpers, panic-catch wrapper, repo/diff/
//! graph/watcher wrappers) lands in Epic 3. The full `zanshin_ffi_version()`
//! implementation with `build.rs` git-SHA injection and `CString` allocation
//! lands in Story 3.2.

use core::ffi::c_char;

/// Build-stamp version string. WIP-placeholder: returns a static C-string pointer
/// to the crate version. Story 3.2 replaces this with a heap-allocated
/// `<version> (<git-sha>)` string via `ffi_strings::string_to_cstring` and a
/// `build.rs` that injects `ZANSHIN_GIT_SHA` at compile time.
///
/// # Safety
/// The returned pointer is a `'static` literal — the caller MUST NOT free it.
/// Story 3.2's replacement returns a heap pointer and pairs with
/// `zanshin_string_free`; the placeholder does not.
#[no_mangle]
pub extern "C" fn zanshin_ffi_version() -> *const c_char {
    // WHY: static null-terminated literal — no allocation, no build.rs needed
    // for the Story 1.5 codegen-plumbing bootstrap. Replaced wholesale in 3.2.
    b"0.1.0\0".as_ptr().cast::<c_char>()
}
```

**Why `*const c_char` not `*mut c_char`:** the literal is read-only. Story 3.2 changes this to `*mut c_char` (heap-allocated, paired with `zanshin_string_free`). The signature change is an intentional WIP breaking change (per `project-context.md` — "breaking changes between WIP versions are allowed, callers update").

**Why no `mod envelope; mod handle; mod ffi_strings;` declarations yet:** those modules are Story 3.1 / 3.2's bodies. Adding empty `mod` declarations now would be speculative scaffolding (per `project-context.md` § "Don't design for hypothetical future requirements").

`git diff --quiet HEAD -- "$HEADER" "$BINDINGS"`:
- `HEAD --`: compares working-tree to HEAD (catches BOTH unstaged AND staged edits).
- `--quiet`: no output, exit code is the signal (0 = clean, 1 = differs).
- `-- "$HEADER" "$BINDINGS"`: scopes to just the two generated files.

The other check forms considered and rejected:
- `git diff --quiet --` (no HEAD): unstaged-only; staged edits would slip through.
- `git status --porcelain $HEADER $BINDINGS | grep -q .`: works but more brittle than `git diff` (porcelain format changes between git versions are rare but possible).

### Why ffigen's `Pointer<Char>` is NOT a `String` (epics.md AC clarification)

The epics.md § Story 1.5 AC line 766 reads:
> **And** `bindings.dart` exposes `String zanshinFfiVersion()` with the proper `Pointer<Utf8>` → Dart String conversion.

This is **misleading shorthand** in the source artefact. ffigen 20.1.1 does NOT auto-convert `const char *` to Dart `String` — the wire-side `bindings.dart` exposes the raw signature: `ffi.Pointer<ffi.Char> zanshin_ffi_version()` (or `zanshinFfiVersion` after ffigen's name transformation).

The `Pointer<Utf8> → Dart String` conversion is **consumer-side code**, written manually using `package:ffi`:
```dart
final ptr = bindings.zanshin_ffi_version();
final version = ptr.cast<Utf8>().toDartString();
```

Story 3.2 introduces a typed Dart-side wrapper that does this conversion as part of the public API. `bindings.dart` itself stays raw — that's ffigen's contract (mechanical 1:1 translation of the C header), and trying to inline `String` conversion would require either ffigen-side type mapping (which it does not support for arbitrary `char *`) or hand-edits to generated code (an AR-AP-7 violation).

Resolution recorded here so the next code-review pass doesn't reopen the question. The Story 1.5 AC-5 is interpreted as "raw ffigen output of the cbindgen header, exposing the symbol with the proper FFI types", NOT "magically auto-convert to `String`".

### Conflict raised + resolved: epics.md AC text on `DynamicLibrary` hardcoding vs. ffigen behaviour

The epics.md § Story 1.5 AC line 757 reads:
> the bindings consist of a `ZanshinFfi` class wrapping `DynamicLibrary.process()` or `DynamicLibrary.open('libzanshin_ffi.dylib')` (configured per macOS bundle layout).

This is **interpretation-loaded**. ffigen does NOT hardcode `DynamicLibrary.process()` or `DynamicLibrary.open(...)` in the generated `bindings.dart`. Instead, ffigen's standard output is a class whose **constructor takes a `DynamicLibrary` argument**:
```dart
class ZanshinFfi {
  ZanshinFfi(ffi.DynamicLibrary dynamicLibrary)
      : _lookup = dynamicLibrary.lookup;
  ...
}
```
The CALLER decides whether to pass `DynamicLibrary.process()`, `DynamicLibrary.open(...)`, a unit-test mock, or anything else. Hardcoding the choice in `bindings.dart` would tie it to one bundle layout and break the test path (where the cdylib path differs from production).

**Resolution:** Story 1.5 AC-5 is interpreted as "the generated class takes a `DynamicLibrary` argument; the caller decides how to obtain it". The "wrapping ... DynamicLibrary.process()" text in epics.md is descriptive of how a future Epic 3 worker isolate will INVOKE the generated class, not a directive for `bindings.dart` itself. Do not hardcode. Recorded here so future review doesn't re-litigate.
