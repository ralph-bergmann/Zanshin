## Deferred from: code review of 3-2-handle-module-ffi-strings-zanshin-ffi-version (2026-06-15)

- **`build.rs` git-SHA stamp goes stale under git worktrees / shallow clones** [`crates/zanshin-ffi/build.rs:20`] — `cargo:rerun-if-changed=../../.git/logs/HEAD` assumes `.git` is a directory two levels up. In a linked worktree (or submodule) `.git` is a *file* and the reflog lives under the common dir; shallow/fresh clones may lack `.git/logs/HEAD`. In both cases the rerun trigger watches a nonexistent path, so the SHA stamp never refreshes when HEAD moves. The spec Dev Notes consciously chose simplicity ("do not over-engineer ref-walking"; a stale stamp "is fine for a build-stamp"). Low-impact (cosmetic build-stamp in WIP). A robust fix derives the path via `git rev-parse --git-path logs/HEAD`. Revisit at release phase or if a worktree workflow is adopted.
- **`build.rs` embeds an unrelated parent-repo SHA instead of `unknown`** [`crates/zanshin-ffi/build.rs:5`] — when the source tree has no own `.git` but sits inside another git checkout, `git rev-parse HEAD` succeeds against the enclosing repo, so a source-tarball-in-a-repo build stamps the wrong SHA rather than the intended `unknown`. Contrived; low impact for a WIP build-stamp.

## Deferred from: architecture discussion — logging sink (2026-06-18, Winston)

- **OSLog sink via `tracing-oslog` not adopted in WIP** [`crates/zanshin-ffi/src/tracing_init.rs`] — A colleague suggested macOS Unified Logging (`oslog` / `tracing-oslog`). It is the macOS-idiomatic sink (Console.app + `log stream`, subsystem filtering) and composes as an *additional* `tracing` layer without touching any call site or the FFI — `zanshin_log` and every `tracing::*` site are sink-agnostic. Deferred to release-phase supportability hardening (alongside the size/age-cap rotation) for three reasons: (1) the plain `~/Library/Logs/Zanshin/*.log` file is far easier for a user to attach to a bug report than an OSLog `.logarchive`/sysdiagnose export; (2) `log show` drops `info`/`debug` by default (memory-only unless `sudo log config … persist` is set), so OSLog is a poor *sole* sink for after-the-fact diagnostics; (3) OSLog does not write to stderr, so it would not surface in the `flutter run`/IDE console — the current debug stderr layer does (verified 2026-06-18: `flutter run` forwards the app's native stderr to the IDE console). Its strongest future payoff is `zanshin-mcp`: OSLog is a clean non-stdio sink that satisfies AR-P-5-MCP natively. Revisit at release as an *added* layer (keep the file as source of truth), verify the crate against the pinned Rust toolchain + current macOS, and record an ADR (touches AR-P-5). Crate: `tracing-oslog` (@Absolucy, permissive zlib/MIT-style license).

- **Console log layer is UNCONDITIONAL during WIP dev — re-gate before ship** [`crates/zanshin-ffi/src/tracing_init.rs`, `crates/zanshin-ffi/Cargo.toml`] — Root cause of the "I see no logs" saga (2026-06-18): the cdylib is built in the `release` profile even under `flutter run`, so the old `cfg!(debug_assertions)`-gated stderr layer was compiled out. Fix made the console (stderr) layer **always on at `trace`** and **removed `release_max_level_info`** so `debug`/`trace` compile in — `flutter run` forwards native stderr, so this is the live dev view (Dart logs arrive via `zanshin_log` too). This DEVIATES from AR-P-5 ("no console output in release builds"): a shipped, Finder-launched app would also emit to stderr (→ Console.app/unified log), and `debug`/`trace` now ship. **Before release:** gate the console layer behind an env var (e.g. presence of `ZANSHIN_LOG`, or a dedicated `ZANSHIN_CONSOLE`), reinstate the `info`-default discipline for the shipped app, and reconsider re-adding `release_max_level_info`. Deferred per Ralph (2026-06-18): during development he does not want to wonder why no logs appear, so console stays unconditional for now.
